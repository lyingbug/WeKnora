# 插件系统调研：业界成熟做法与我们的差距

在继续往下写之前，先看清楚成熟系统是怎么做的。本文记录调研结论、我们当前实现的差距，以及据此修正的设计。

## 一、业界做法横向对比

| 系统 | 声明式层 | 代码层 | 代码层的隔离 | 分发 |
|---|---|---|---|---|
| **Airbyte** low-code CDK | YAML：requester / authenticator / paginator / record selector / error handler | 自定义 Python 组件 | 进程内（视为可信） | 连接器注册表 + 镜像 |
| **n8n** | 声明式节点 `routing` JSON | 编程式 `execute()` | 进程内（视为可信） | 带版本的 npm 包 |
| **Dify** | provider YAML（tool / model / endpoint） | Python 插件 | **独立进程**（stdin/stdout）、Serverless、或远程调试 TCP | 打包 + 市场 + 审核 + 权限声明 + 隐私政策 |
| **Terraform / Grafana** | schema | Go | **子进程 + gRPC**（hashicorp/go-plugin） | 注册表 + 协议版本化 |
| **Extism / wazero** | — | 任意语言编译成 WASM | 进程内 WASM 沙箱 | `.wasm` 产物 |
| **MCP** | — | 任意语言的 server | 独立进程 / HTTP | server 目录 |

### 三条几乎一致的结论

**1. 声明式为主 + 代码为辅，是共识而不是取舍。** n8n 的文档写得最直白：绝大多数节点应该用声明式，只有触发器、非 REST、需要外部依赖或复杂数据变换才用编程式。Airbyte 同样把 low-code YAML 作为主路径，Python 组件作为例外。这一点我们的方向是对的。

**2. 声明式层的词汇表比我做的丰富得多。** Airbyte 把这些做成了一等组件：

- `authenticator`：Bearer / ApiKey / Basic / OAuth / SessionToken
- `paginator`：page increment、offset、cursor 三种策略，加上 token 注入位置
- `error_handler`：状态码到动作的映射、退避策略
- `record_selector`：提取路径 + 记录过滤
- `check`：连接可用性检查
- `definitions` / `$parameters`：清单内复用

这些不是锦上添花——它们恰恰是每个集成都会重写一遍的东西。我的格式一个都没有。

**3. 没有一个成熟系统把不可信插件代码直接跑在主进程里。** Dify 用独立进程（daemon 通过 stdin/stdout 通信），Terraform 和 Grafana 用子进程加 gRPC，WASM 阵营靠运行时内存隔离。Extism 的安全分析把风险说得很准：**WASM 沙箱隔离的是内存，而宿主函数是跑在沙箱外的原生代码**——一个能发任意 HTTP 请求的宿主函数，会把沙箱插件变成应用级后门。

## 二、我们当前实现的差距

对照上面这三条，诚实评估：

### 做对的

- 声明式优先、代码兜底的分层，与 n8n / Airbyte 一致。
- 插件是文件、热加载、坏文件隔离、加载时校验。
- 请求体用结构化类型化替换而不是文本模板，从构造上消除了注入。这一点比很多实现更稳。

### 不足的

**声明式层太薄。** 没有 authenticator、没有分页、没有错误重试策略、没有记录过滤、没有清单内复用。现在每个插件都得把认证头手写一遍；一旦遇到需要翻页的搜索 API，声明式层就直接失效，只能退到脚本——而这正是把逃生舱变成常态的路径。

**脚本层的隔离弱于业界水位。** 我用 goja 在进程内跑 JS，靠"只注入白名单全局变量"来约束。goja 确实隔离了 Go 内存，但真正的边界是我注入的 `http` 函数，而它**没有出站域名白名单**——插件可以请求任意外部地址（SSRF 检查只挡内网，不挡数据外发）。Extism 那篇分析点名的就是这个模式。Dify 之所以把插件放进独立进程，正是为了这个。

**缺少版本与兼容策略。** 只有一个 `apiVersion: weknora/v1`。没有插件自身版本、没有"要求宿主 ≥ 某版本"、没有协议演进路径。Terraform 的经验是：协议一旦长到极限，只能整体不兼容重来。

**没有权限声明。** Dify 的清单里插件要声明它请求什么权限、如何使用用户数据。我们的插件拿到的是同一套能力，没有分级。

**没有打包与完整性。** 一个裸 YAML 文件，没有签名、没有校验和、没有出处。作为"运维自己放进去的文件"尚可，作为"从社区下载的插件"完全不够。

**没有连接检查。** Airbyte 的 `check`、n8n 的凭据测试，都是"保存前先验证一下能不能通"。我们只有保存后调用时才知道。

**没有用上已有的 MCP。** 这个仓库已经集成了 MCP 客户端。MCP 就是业界给"进程外工具插件"的标准答案，而我在旁边另起炉灶。

## 三、据此修正的设计

### 分三层，各有明确定位

| 层 | 机制 | 适用 | 隔离 | 谁能加 |
|---|---|---|---|---|
| **L1 声明式** | YAML（扩充为 Airbyte 那套词汇） | 绝大多数 HTTP 集成 | 不需要——它只是数据 | 任何人，放文件即可 |
| **L2 脚本** | 沙箱脚本 | 抓页面、翻页边界、签名推导 | 沙箱 + **出站白名单** + 配额 | 部署方（需显式开启） |
| **L3 进程外** | MCP server / go-plugin | 重逻辑、有状态、任意语言 | 进程边界 | 任何人，独立发布 |

关键判断：**L1 要尽量厚，L2 要尽量薄。** 每当有插件被迫用 L2，都应该先问"L1 缺了什么组件"，补上之后所有后来者受益。这正是 Airbyte 把 paginator 和 authenticator 做成一等组件的原因。

### L1 需要补的组件（按优先级）

1. **authenticator** —— `bearer` / `api_key`（含注入位置：header/query）/ `basic`。目前所有插件都在手写 `Authorization: Bearer ${config.api_key}`。
2. **error_handler** —— 状态码到动作（重试/失败/忽略）的映射与退避。现在任何 429 都是直接失败。
3. **paginator** —— 至少支持 cursor 与 page increment。没有它，翻页类 API 只能落到 L2。
4. **check** —— 保存配置前的连通性验证。
5. **record filter** —— 简单的布尔表达式过滤。

### L2 的隔离必须补强

如果保留进程内脚本（goja），至少要有：

- **出站域名白名单**：写在清单里，由宿主强制。插件只能访问它声明过的域名。这是 Extism 分析里明确建议的缓解措施，也是把"能发任意请求"降级为"能发声明过的请求"的唯一办法。
- **默认关闭**：脚本插件需要部署方在配置里显式开启，未开启时只加载 L1 插件。
- **配额**：已有超时和请求数上限，还需要内存与输出大小上限。

如果不接受进程内执行，替代方案是把 L2 直接并入 L3（脚本插件跑成独立进程），代价是运维复杂度和延迟——Dify 选了这条路。

### L3 优先复用 MCP

这个仓库已经有 MCP 客户端。与其自己定义一套进程外插件协议，不如把 L3 直接落在 MCP 上：一个重逻辑插件就是一个 MCP server，用现成的传输、现成的生态、现成的调试工具。自定义协议只在 MCP 表达不了的能力上才考虑。

## 四、待确认的问题

1. **脚本插件跑在进程内还是进程外？** 进程内延迟低、部署简单，但隔离弱于业界水位；进程外符合 Dify/Terraform 的做法，但要引入进程生命周期管理。倾向：进程内 + 出站白名单 + 默认关闭，先服务"部署方自己写脚本"这个场景；社区插件走 L3。
2. **插件要不要版本与来源校验？** 如果只面向"运维放文件"，可以先不做；如果计划做插件市场，版本、签名、权限声明要一开始就进清单，后加会是破坏性变更。
3. **L1 的组件补到什么程度？** 全套照搬 Airbyte 会让格式变重。建议先补 authenticator 和 error_handler（每个插件都要），paginator 按需。
