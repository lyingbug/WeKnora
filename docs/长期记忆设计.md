# 长期记忆设计

> 对应 Roadmap 条目：`知识库形态 → 探索知识库与 Memory 结合的应用场景`（见 [`docs/ROADMAP.md`](./ROADMAP.md)）
>
> 本文描述已实现的第一期。写下它不是为了完整，而是为了让后面的人知道**每条约束为什么在这里**——这个功能在 WeKnora 里已经死过两次，两次的死因都记录在下面。

## 1. 它解决什么

在此之前，WeKnora 有三个容易被当成记忆、但都不是记忆的能力：

| 能力 | 位置 | 为什么不是长期记忆 |
|---|---|---|
| 多轮历史 | `internal/application/service/chat_pipeline/load_history.go` | 只在单个 Session 内有效，换个会话就没了 |
| Agent 上下文巩固 | `internal/agent/memory/consolidator.go` | 纯进程内，一次请求结束即消失 |
| 会话历史知识库 | `internal/application/service/message.go` 的 `IndexMessageToKB` | 租户级原始消息向量库，不属于某个人，无结构、无去重、无冲突处理 |

长期记忆补的是这一条：**跨会话地、属于某一个人地、可累积可纠正地**记住他说过的关于自己的事。

## 2. 前两次为什么失败

**第一次**（v0.3.2 引入，v0.7.1 由 PR #2130 整体删除）：基于 Neo4j 存 `:Episode` / `:Entity`，读路径先用 LLM 抽关键词再查图，写路径再调一次 LLM 抽实体关系。`MemoryService` 的每个方法都以 `repo.IsAvailable(ctx)` 开头，而 Neo4j 默认不开——对绝大多数用户，这个功能等价于不存在。除了一个设置开关外没有任何界面。

**第二次**（分支 `cursor/plan-long-term-memory-wiki-e57e`，未合并）：20082 行、111 个文件，一次性做了记忆页面化并复刻整套 Wiki 语义、记忆与知识库的锚点「点亮」层、桥接图谱、k-匿名洞察、分类型指数半衰期、44 个键的分层设置系统。它自己的文档列出了三十多条缺陷，其中最关键的一条是：聊天侧的可见性完全没有实现——记忆在对话里生效，但用户看不见。

**所以本设计有三条不可协商的约束：**

1. **不引入任何新依赖。** 只用主库（PostgreSQL / SQLite）和既有的任务队列抽象。没有 Neo4j，没有新的向量库，没有新的缓存。
2. **可见性是第一期交付物，不是后续增强。** 用户看不见、改不了、删不掉的记忆不能上线。
3. **范围优先于完备。** 第一期只做记忆本身；与知识库 / Wiki 的关联留到底座稳定之后。

## 3. 数据模型

两张表。

`memory_subjects` 是记忆空间，`(tenant_id, subject_id)` 唯一。`subject_id` 取 `Principal.StorageID()`，因此 Web 用户、IM 用户、API 外部用户、Embed 访客都能各自拥有空间而不需要 WeKnora 账号。它还缓存渲染好的常驻块和防抖时间戳。

`memory_items` 每行是一句话，字段中值得说明的是：

- `topic` 是抽取模型给出的可读主题（「在用的数据库」），**原样保存**。它是最好的检索线索：提问往往点名主题，而陈述句只带取值（「已经迁到 PostgreSQL」）。
- `normalized_key` 是 topic 归一化后的碰撞键，用于发现矛盾。它是排序去重后的字符串，**不能拿来做检索**（词序已被破坏）。
- `valid_from` / `invalid_at` / `superseded_by` 是双时间。矛盾信息不物理删除：旧条目写 `invalid_at`，新条目回填 `superseded_by`，于是「记忆为什么变了」在界面上可解释。这是从 Zep / Graphiti 借来的唯一一件事，图部分没有借。

作用域**永远从请求上下文推导**，没有任何接口接受 subject 参数。这不是为了少写校验，而是为了让「能不能改个 id 读到别人的记忆」这个问题根本不存在。

## 4. 读路径：零模型调用

每轮注入两段：

**常驻块**是渲染好的一段文本，直接从 `memory_subjects` 主键读出，只在写入时重算。内容是稳定特征（`profile` / `preference`），**加上所有用户显式要求记住的条目**——不论它是什么类型。后半条是手动验证逼出来的：用户说了「记住我的编辑器是 Neovim」，接着问「我平时用什么工具」，两句话没有一个词重叠，纯靠词法匹配就召不回来。用户唯一亲口要求记住的那条，恰恰最不该丢。

**情境召回**对 `fact` / `task` 做词法打分，取最相关的若干条。分词对 CJK 逐字切分并计算二元组（单个汉字「数」出现在数据、参数、数量里，噪声太大），相关度低于阈值的一律不注入——一条只是碰巧共享一个词的旧记忆，比没有记忆更糟。

第一期**不用向量**。单个空间的量级是几百条，词法足够，且不引入依赖。这一点写死在设计里，而不是设计写向量、实现改词法然后打补丁。等真实数据证明词法不够，再复用现有 `RetrieveEngineRegistry`，那时它是一个独立可验证的增量。

两条链路各一个接入点：RAG 走 `MEMORY_RECALL` 插件（`chat_pipeline/memory_recall.go`），Agent 走 `AgentEngine.SetMemoryPrompt`。Agent 侧必须走系统提示，因为 `buildMessagesWithLLMContext` 会丢弃来自历史的 system 消息——单独发一条记忆消息从第二轮起就静默消失了。

记忆内容包在 `<user_memory>` 标记里，并明确声明是背景数据而非指令。一旦用户写的句子进了系统提示，这是唯一能做的防线。

## 5. 写路径

**显式写入**是同步的、确定的：用户说「记住：……」或 `remember that ...`，前缀命中就原样落库，中间没有模型。这让默认档位 `explicit_only` 是有用的，而不只是安全的。

**隐式提炼**是异步的：会话结束后入队 `TypeMemoryExtract`（Lite 无 Redis 时走 `SyncTaskExecutor`），跑一次 LLM，输出 `ADD` / `UPDATE` / `DELETE` 决策（Mem0 的做法）。

抽取**只读 `role=user` 的消息**。助手自己的输出是模型在跟自己说话，把它喂回抽取，正是检索到的文档里的提示注入变成「关于用户的长期事实」的路径。

任务需要的一切都在 payload 里（tenant、subject、session、message、会话所用模型）。asynq 和 Lite 执行器都从一个空 context 起步，请求当时知道而 payload 没带上的东西，到 worker 手里就没了——上一版正是在这里静默失败。

### 5.1 覆盖性：开关开着时，没有一条消息会被丢掉

第一版的调度是拿当前时间和上次运行时间比，落在最小间隔内就直接 return。后果是那个窗口里的每一轮对话都被**静默丢弃**：功能看着是开的，实际什么都没学到。一次运行也只读触发它的那个会话最近的若干条消息，于是并行的第二个会话、以及一次说得太多的用户，都读不到。

现在覆盖性是**数据的性质，而不是时序的性质**：

- `memory_subjects.extract_cursor` 是水位线，运行时从它往后走。
- `pending_sessions` 是有未处理轮次的会话队列。一轮对话到来时若已有任务在途，它加入队列而不是被丢弃。
- `extract_scheduled_at` 是在途标记，让一串连发的对话只产生一个任务而不是每轮一个；标记会过期，避免 worker 崩溃后把这个人永久卡死。
- 队列在运行**开始时**就被取走。运行期间到来的轮次落进新队列并触发后继运行，而不会被这次没看见它们的运行抹掉。
- 一次运行读到消息上限、或运行期间又来了新轮次，都会排下一次运行。
- 运行失败时水位线不动——它没读成功的消息必须被重读，而不是被跳过。

最小间隔现在只**推迟**运行，从不丢弃轮次。它和挖掘延迟一样是工作空间设置项，不再是常量。

`internal/application/service/memory/coverage_test.go` 就是为这条性质写的：在防抖窗口内连发多轮、跨两个会话、一次说的比单次运行上限还多、运行失败，都断言每一句最终都被模型读到。把旧的丢弃逻辑放回去，这些测试会失败。

去重有两层：同一 topic 键走 supersede；内容互相包含的走合并（「我们的生产库是 X」和「生产库是 X」是同一件事，但 topic 键不同，只靠键匹配会让用户看到重复的记忆）。

## 6. 遗忘：三条规则

不做衰减曲线（上一版把分类型指数半衰期算成了复利，profile 第 45 天就被归档）。只有：容量上限后按重要度与使用时间归档、用户手动删除、用户一键清空。每一条都能用一个断言测出来。

## 7. 可见性

- 设置 → 账户 → **我的记忆**：看、加、改、删、导出、一键清空，每条显示类型、来源与时间。
- 聊天回答上方：「本次使用了 N 条记忆」，作为**时间轴里的一个步骤**渲染，展开可见具体内容，悬停某行即可删除该条。

记忆节点复用 `RagPipelineProgress` 的树状节点结构，而不是自带一套卡片样式：召回记忆是这一轮回答前做的又一件事，给它单独的视觉语言只会让它读起来像与流程无关的东西，而且两套样式必然随时间漂移。纯聊天没有自己的流水线，但用到了记忆的那一轮仍有话要说，因此它渲染同一个时间轴组件，只是里面只有这一个步骤。

第二条不是加分项。用户注意到一条错误记忆的时刻，就是它影响了某个回答的时刻；让他在那一刻就能删掉，是这个功能能否被信任的分界线。

## 8. 配置：4 个键

工作空间开关（默认关）、写入方式（`explicit_only` / `auto`）、提炼模型（留空则用会话模型）、挖掘延迟、两次挖掘的最小间隔、每人容量上限；外加用户级开关和 Agent 级 `memory_enabled`。后两者**只能收紧**，不能放开工作空间的决定。

两个时间参数都有下界，且下界是成本考虑而不是安全考虑：延迟接近零会把一串连发的消息变成一次调用一条。

默认关是因为这个功能会留存用户说过的话。代价是它容易被忽略，所以空间设置页顶部用一段说明讲清楚开启后会发生什么——上一版「默认关 + 没有引导」等于功能不存在。

## 9. 验证方式

上一版复盘出的根因是「声明了但没接上，而测试进入的位置在接缝之下」。因此：

- 写路径的测试从门控进入，断言数据库里最终有什么，而不是直接调内部服务。
- 后台任务的测试用**空 context** 调用 handler，断言作用域是从 payload 重建的。
- 召回的测试断言最终 messages 里那段文本存不存在，而不只是 recall 返回了什么。
- `internal/application/service/memory/regression_test.go` 是中文跨会话回归集：记住画像、偏好常驻、按相关性召回、修正矛盾、续接在办事项、完成后不再召回、一次性提问不入库。
- `internal/application/service/memory/coverage_test.go` 断言开关开着时没有一条消息被丢掉，见 [5.1](#51-覆盖性开关开着时没有一条消息会被丢掉)。

不使用 LoCoMo / LongMemEval 打分：其公开数字基本由厂商自跑，同一基准上不同来源相差数十个点，且没有与实际用法匹配的中文切分。
