# 长期记忆：业界方案源码对比

这份文档不是综述。五个项目全部 clone 到本地读了源码，提示词逐字提取，关键常量带 file:line 核对过，其中 mem0、Letta 两个还把真实代码跑起来看了中间结果。目的只有一个：判断我们自己的实现哪里落后、哪里领先、哪些该改。

读的版本：

| 项目 | 版本 / commit | 规模与性质 |
|---|---|---|
| mem0 | `c427a45`，包版本 2.0.18 | 抽取流水线 + 向量检索 |
| Graphiti (Zep) | `401c59a` | 时序知识图谱 |
| Letta (legacy) | `ff19ffe` | 自述「维护模式」，数据库 block 模型 |
| letta-code | 2026-08-12 | Letta 的活跃实现，git 托管的记忆文件系统 |
| LangMem | HEAD | 无状态原语 + 提示词自优化 |
| Cognee | `4b9dd36` | 文档摄取平台 + 本体接地 |

完整报告见 `/opt/cursor/artifacts/` 下的 `mem0_memory_report.md`（2023 行）、`graphiti_temporal_kg_memory_report.md`（3126 行）、`letta_code_memory_model_report.md`（1528 行），以及 mem0 与 Letta 的真实运行日志。

## 1. 其实只有三种架构

五个项目看起来各不相同，落到「记忆从哪来、到哪去」只有三条路线。

**路线一：流水线抽取 + 向量召回**（mem0、LangMem、Cognee）。对话进来，LLM 抽成条目，向量入库，检索时按相似度取回。差别在细节：mem0 是单次 ADD-only 调用，LangMem 用 JSON Patch 按 id 打补丁，Cognee 抽成图并对齐本体。

**路线二：时序知识图谱**（Graphiti）。抽实体和关系，做实体消解，用双时间轴处理矛盾。它是唯一一个把「这条事实什么时候开始为真、什么时候被推翻」当作一等公民的。

**路线三：智能体自管理**（Letta）。没有抽取流水线。记忆是文件，智能体用工具自己改，改不改、改什么由模型判断。letta-code 把它推到极致：记忆就是一个 git 仓库，`system/` 下的文件进系统提示，其余只暴露路径，靠 `grep` 找。

我们属于路线一，但混入了路线二的双时间轴（supersede + `valid_from`/`invalid_at`）。

## 2. 构造侧：逐环节对比

### 2.1 抽取前，喂给模型多少条已有记忆、怎么选

这是我第一个发现自己做错的地方。

| | 候选数量 | 选取方式 |
|---|---|---|
| mem0 | 硬编码 top_k=10 | 整段对话做向量检索（`main.py:923-938`） |
| Graphiti | 每个待判实体 ≤15，0.6 分数下限 | 按实体名做纯余弦（`_semantic_candidate_search`） |
| LangMem | `query_limit` 默认 5 | 可选 LLM 生成查询，否则对指数扩张的尾部窗口做检索 |
| **我们** | **最多 60 条** | **不筛选，按重要度/时间取前 60** |

我们把最多 60 条记忆不加语义筛选地塞进提示。条数一多，判断质量下降、成本线性上涨，而且和当前对话无关的记忆会干扰模型的 update/delete 决策。三个参照系统都用语义检索取一个小得多的候选集。

顺带一提，mem0 把 UUID 映射成整数下标再喂给模型，代码注释写明是 `# Map UUIDs to integers (anti-hallucination)`。我们用的也是下标，这条算独立收敛。

### 2.2 抽取调用的次数与形态

| | 调用次数 | 输出形态 |
|---|---|---|
| mem0 v2.0.18 | **1 次**，ADD-only | `{"memory":[{"id","text","attributed_to","linked_memory_ids"}]}` |
| Graphiti | 一次 episode 至少 4~5 次（节点抽取、节点消歧、边抽取、边消歧+失效、属性与摘要） | 每步一个 pydantic schema |
| LangMem | 1 次（多步模式下最多 `max_steps`） | 并行多工具调用：新建 / `PatchDoc` / `RemoveDoc` |
| Cognee | 每个 chunk 2 次并发（图抽取 + 摘要） | `KnowledgeGraph{nodes,edges}` / `SummarizedContent` |
| Letta | 0 次流水线调用 | 智能体自己发工具调用 |
| **我们** | 每段 1 次，另加可选的主题判定与离线巩固 | `{"memories":[...],"topics":[...]}` |

关于 mem0 有一条值得单独写：**它现在只有一次 LLM 调用，而且是纯 ADD**。广为流传的「ADD/UPDATE/DELETE/NONE 双调用架构」在 2.0.18 里已经没有调用方了——`DEFAULT_UPDATE_MEMORY_PROMPT` 还留在 `prompts.py:176-324`，但只有测试引用它。也就是说 **mem0 开源版没有冲突消解**：矛盾的记忆并存，谁也不推翻谁。这一点它自己的 issue #4904 也承认。

同样值得记一笔：**mem0 把图记忆整体移出了开源版**，约 4000 行，且明说不提供开源替代（`docs/migration/oss-v2-to-v3.mdx:334-343`）。我自己 grep 核对过，`mem0/` 下只剩 `exceptions.py` 一处提及。业界最常被引用的那套主动砍掉了图——这是我们当初决定不建图谱的一个有力旁证。

### 2.3 去重与实体消解

| | 机制 | 阈值 |
|---|---|---|
| mem0（记忆） | MD5 精确哈希 | 一个字符之差即失效 |
| mem0（实体） | 归一化精确匹配 or 余弦 | **≥ 0.95**（裸字面量，`main.py:621/1152`） |
| Graphiti | 三层：精确 → MinHash/LSH → LLM | **Jaccard ≥ 0.9**，32 permutation，band 4，香农熵 ≥ 1.5 门控 |
| Cognee | 类命名空间的确定性 id（`uuid5(类名:归一化名)`）+ 本体模糊匹配 | 同名即同节点，跨文档跨运行 |
| LangMem | 只有 `(namespace, key)` 精确身份 | 其余靠提示词让模型自己合并 |
| **我们** | 三层：精确+别名 → 字符 2-gram Dice → LLM | **Dice ≥ 0.80** |

分层结构上我们和 Graphiti 一致，这是好事。但**阈值的严格程度差一大截**：Dice 和 Jaccard 可换算，`D = 2J/(1+J)`，所以我们的 0.80 相当于 Jaccard 0.667，而 Graphiti 要求 0.9（换算成 Dice 是 0.947）。

要公平地说：对象不同。Graphiti 匹配的是实体名（短、近乎同形），我们匹配的是描述性主题短语，天然更长更松。我们评测集实测的间隔是 0.60–0.83，0.80 落在缝里——但只比「详略差异」那一例低 0.03，余量很薄。

Cognee 那条路值得单独想一想：**它根本不做相似度判断**，而是用「类名 + 归一化名」算确定性 uuid5，同名就是同节点。`DataPoint.id_for` 的注释说得很直白——没有 `identity_fields` 的节点拿随机 uuid，「永远不会跨运行去重」。把身份变成可计算的属性，而不是每次去猜，这是另一种解法。

### 2.4 矛盾处理

这是差距最大的一环，而且不是我们落后。

| | 做法 |
|---|---|
| mem0 OSS | **无**。矛盾记忆并存 |
| Cognee | **无**。grep `contradict` 只命中 HTTP 409 和 `ON CONFLICT` |
| LangMem | 提示词里一句「update it based on the new information」 |
| Letta | 提示词里一句「fix the stale entry at the source」 |
| Graphiti | **真正实现了**：LLM 提出矛盾，再由确定性区间算术裁决 |
| 我们 | supersede + 双时间轴 + 墓碑 |

Graphiti 的裁决规则值得抄：**只有当两条边都有日期、且旧边严格更早生效时才失效旧边；没有日期的边永不失效**。旧边不删除，`invalid_at` 设为新边的 `valid_at`，`expired_at` 打上墙钟时间。

我们现在是「同主题即取代」，不看时间。这在「生产库从 MySQL 换成 PostgreSQL」这种场景对，但在「两条同主题、都没有时间信息的陈述」上会误伤——后到的无条件取代先到的，哪怕它并不更新。

### 2.5 离线整理

| | 有无 | 形态 |
|---|---|---|
| mem0 | 无 | 全部内联在 `add()`/`search()` |
| LangMem | 有 | `ReflectionExecutor`，按 thread 去抖，新提交取消旧的 |
| Letta | 有 | 反思子智能体，在 **git worktree** 里工作，改不动主检出 |
| Cognee | 有 | `memify` 管线：反馈权重、频率权重、实体描述合并 |
| Graphiti | 有 | 社区检测与摘要 |
| 我们 | 有 | 每人每天一次整库回顾，搭在抽取任务尾部 |

Letta 的 worktree 隔离是这里最讲究的：后台整理跑在独立分支上，父仓库脏了就中止合并而不是覆盖用户未提交的改动。我们的巩固是直接改主表的。

## 3. 使用侧：记忆怎么进到回答里

### 3.1 召回信号

| | 召回方式 |
|---|---|
| mem0 | 向量 + BM25 + 实体加权融合。**候选只来自向量结果**，BM25 和实体只重排不召回 |
| Graphiti | 向量 + 全文 + 图遍历，RRF 融合（`rank_const=1`，不是常规的 60），可选 MMR（λ=0.5）、节点距离、cross-encoder |
| Cognee | 一次 query embedding 打到全部向量集合，取 100 候选，投影成子图后按整条三元组打分 |
| Letta | 记忆**没有检索**。`system/` 直接在上下文里，其余靠模型 `grep` |
| LangMem | store 的向量检索 |
| **我们** | **纯词面**：unigram + bigram 打分 |

**这是我们唯一明显落后的环节。** 除 Letta 外全部用向量，而 Letta 之所以能不用，是因为它把记忆做成了「常驻 + 按路径读」，根本不需要相关性排序。我们是「常驻 + 按相关性召回情境记忆」，却用词面匹配来做那个相关性——换个说法就召不回。

好消息是接入成本低：仓库里已经有 pgvector + HNSW（`migrations/versioned/000002_embeddings.up.sql`）和一层支持 10 种后端的 retriever 抽象（含 sqlite）。

mem0 有个细节要注意：它的 `threshold` 卡的是**融合前的原始语义分**，所以一条词面完全命中但语义偏远的记忆永远救不回来。如果我们做混合召回，别踩这个。

### 3.2 上下文经济学

Letta 的两层结构和我们的设计是同一个：

| Letta | 我们 |
|---|---|
| `system/**.md` → 全文进系统提示 | resident block（profile/preference 常驻） |
| 其余 → 只暴露路径/描述，按需读 | situational（按查询匹配后注入） |
| `skills/**` → 单独广告 | — |

差别在于 **Letta 把这个分层做成了用户可见、可搬移的**：把文件从 `system/` 移到 `reference/` 就把它踢出上下文，反之亦然，而且这个操作模型和用户都能做。我们的 resident/situational 是按 kind 硬编码的，用户改不了。

### 3.3 记忆写入的可追溯性

Letta 要求**每一次记忆写入都带一个 `reason`**，schema 里写明「Required commit message for this memory change. Used as the git commit message.」，然后原样作为 git commit subject 持久化，作者是 `<agent-id>@letta.com`。

我们每条记忆有 `source_session_id` / `source_message_id`，能追到来源消息，但**没有「为什么写这条」**。对一个把可审计当第一优先级的功能来说，这是个便宜且明显的缺口。

## 4. 我们领先的地方

这几条在五个项目里**全部缺失**，每个子报告都显式 grep 核对过：

- **推断进收件箱等确认**。没有任何一个系统对「系统推断出的关于用户的信息」设确认环节。Letta 的 `merge: "explicit"` 看着像，实际是把提案交给**另一个智能体**审，不是人。
- **PII 脱敏**。全部缺失。mem0 的 `pii` 只命中配置密钥的遥测脱敏，Graphiti 的两处命中都是日志卫生注释。
- **删除后不复现（墓碑）**。全部缺失。删了就是删了，下次再抽出来照样写回。
- **「开关开着就一条消息不丢」的水位线保证**。全部缺失。
- **主题计数 / 关注面**。全部缺失，Cognee 的频率权重是最接近的。

最后一条要诚实地说：**没有参照实现，正是我们那块反复改了四轮的原因**。字符袋键、相关性误当同一性、合并后的命名、粒度——每一轮都是上一轮过校正的结果。没有人做过这件事，也就没有人踩过这些坑给我们看。

## 5. 应该改的

按「收益 / 成本」排序。

### 5.1 给记忆召回接向量（高收益，中成本）

我们是五个里唯一纯词面召回的。设施现成。做法建议对齐 mem0 的融合而非替换：向量做召回，现有的词面打分作为一路信号参与融合，而不是直接换掉——词面匹配对精确术语（版本号、错误码、产品名）反而更准。

注意不要复制 mem0 把阈值卡在融合前语义分的做法。

### 5.2 抽取候选按语义筛选（高收益，低成本）

现在把最多 60 条不加筛选地塞进提示。改成「按当前对话向量检索取 top N」，N 取 10~15（mem0 用 10，Graphiti 用 15）。依赖 5.1 的向量能力，做完顺手就能改。

### 5.3 supersede 加时间条件（中收益，低成本）

抄 Graphiti：只有当新旧两条都有可比的时间信息、且旧的严格更早时才让新的取代旧的；两条都没有时间信息时，倾向于并存而不是覆盖。现在「同主题即取代」会让后到的无条件赢。

### 5.4 每次写入带一个 reason（中收益，低成本）

抽取决策里加一个 `reason` 字段，存进 `memory_items`，在「我的记忆」里展示。对一个主打可审计的功能，这是最便宜的一次可信度提升。

### 5.5 巩固跑在快照上（中收益，中成本）

Letta 的 worktree 隔离思路：离线整理不要直接改主表。至少做到「整理期间用户手动改过的条目不被覆盖」——我们现在只在改名那条路径上做了这个检查（内容仍逐字等于旧标签才改），巩固合并那条路径没有。

## 6. 明确不该抄的

- **不要建知识图谱。** mem0 主动砍掉了 4000 行图代码并明说不提供开源替代。Graphiti 的图是有价值的，但它的价值来自时序推理，而时序推理我们已经用双时间轴拿到了大部分。
- **不要把记忆交给智能体自管理。** Letta 那套的前提是「一个长期存活、有自己文件系统的智能体」。WeKnora 的形态是知识库问答，一次问答里让模型自己决定改哪条记忆，延迟和不确定性都不划算。它的**分层思路**值得抄，**自管理**不值得。
- **不要引入本体。** Cognee 的本体接地很漂亮，但它假设有人来写和维护那份 OWL/RDF。我们的用户不会有。
- **不要做提示词自优化。** LangMem 那套（元提示 + 变量校验 + 多提示词归因）是真本事，但它优化的是智能体的行为指令，不是记忆内容，和我们要解决的问题不是一回事。

## 7. 一条方法论上的收获

这五个项目里，凡是「判断」类的问题——该不该记、是不是重复、是不是矛盾、什么时候过期——绝大多数都是交给模型按提示词做的，只有 Graphiti 在实体消解和时间失效两处用了确定性算法兜底。

我们的做法更接近 Graphiti：能用确定性规则判的先判，判不了才问模型，而且模型只有否决权没有自由裁量权。这个方向是对的。但代价是**每一条规则都得自己调**，没有现成参数可抄——主题识别改了四轮就是这个代价的具体形态。所以评测集不是可选项，它是这条路线唯一的刹车。
