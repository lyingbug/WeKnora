# WeKnora 长期记忆重构方案

> 状态：核心数据契约、写入、召回和管理界面已完成第一轮重构。
> 目标：从“功能很多的 Memory Wiki”收敛为用户能理解、能信任、能验证有效性的聊天记忆。

## 1. 产品结论

长期记忆不是把聊天内容尽可能多地存进知识图谱。它只需要清楚地回答四个问题：

1. 哪些内容是用户明确要求一直记住的？
2. 哪些内容只是从历史聊天中归纳、可能随时间变化？
3. 当前问题为什么需要使用这条记忆？
4. 用户如何查看、纠正和删除它？

因此系统采用两个层次：

- **已保存记忆（Saved Memory）**：用户说“记住……”、手动新建、编辑、置顶或确认候选后形成。跨会话稳定存在，所有类型均进入召回候选，不自动衰减；自动抽取不能覆盖它。
- **聊天历史记忆（Chat History Memory）**：后台从用户消息归纳。只有与当前问题相关时才注入，可衰减、归档或被后续事实更新。

这与 ChatGPT 对 Saved Memories 和 Reference Chat History 的公开产品边界一致：前者用于用户明确要求保留的内容，后者动态引用过去聊天且不会保留每个细节。

## 2. 第一版方案的问题

- “记住我偏好中文简洁回答”默认写成 `episode`，而默认常驻召回只读 `profile/preference`，形成“存了但用不上”。
- 自动抽取只有宽泛 `subject`；页面 slug 使用“类型 + 主体”，同一项目的数据库、语言、部署方式会互相覆盖。
- 每个候选都绑定窗口末尾最多十条用户消息，来源看似精确，实际无法证明哪句话支持哪条记忆。
- 自动抽取无法生成白名单结构化偏好，因此真正能影响语言、详略、格式的偏好几乎只能靠编辑器手填。
- `profile/preference/open_question` 大量常驻，未解问题还绕过主 token 预算，长期使用后会挤压问题与知识库上下文。
- 知识库 boost 读取空间内全部 anchor，与当前召回记忆无关，容易形成“过去引用越多、以后越容易继续引用”的反馈环。
- 图谱、点亮、掌握度做了很多代码，但没有证明它们提高了跨会话回答准确率；“掌握度”也主要来自被引用次数，不等于真正理解。
- 用户看不到清晰的“明确保存”和“系统归纳”边界，难以建立信任。

## 3. 新的数据契约

### MemoryPage

- `saved: bool`：明确保存与聊天归纳的边界。
- `memory_key: string`：细粒度事实槽，例如 `preference/language`、`project/weknora/database`。
- 只有相同 `memory_key` 的自动事实才允许更新；宽泛的 `subject` 不再承担冲突判断。
- `saved=true` 不参与自动衰减；自动候选若与 saved page 冲突，候选被拒绝，不改写用户明确保存的内容。

### MemoryNote

- `memory_key`：把事实槽从抽取一直带到归并。
- `structured`：把结构化偏好从抽取一直带到 page。
- `source_message_ids`：抽取器必须返回 `[mN]` 证据标签，服务端只接受能映射到真实 user message 的标签。无证据候选直接丢弃。

## 4. 写入链路

### 显式写入（热路径、零额外模型调用）

`记住……` → 规则识别 → 常见偏好/身份/项目分类 → `saved=true` page + exact message note → 下一轮可召回。

常见偏好被转换成白名单字段，如 `language=zh`、`verbosity=concise`。分类不确定时仍存为 saved episode，不会因为类型判断失败而“记住但用不上”。

### 自动归纳（后台路径）

会话窗口 → 仅 user 消息且带 `[mN]` 标签 → 一次结构化抽取 → 安全与证据校验 → note → 按 `memory_key` 归并为 `saved=false` page。

不新增向量库、图数据库或常驻服务，Lite 与标准版继续使用主数据库；这是有意的基础设施约束，不是临时降级。

## 5. 召回链路

1. 已保存记忆优先进入候选，不再依赖 page type。
2. 聊天历史记忆用当前 query 做保守相关性召回。
3. 未解问题只在“继续、上次、进展、todo”等延续语义出现时召回，并做相关性排序。
4. 预算按最终渲染块计算，包含 header、结构化偏好、普通记忆和未解问题。
5. 知识库 boost 只使用本轮已召回记忆所连接的 anchor，不读取空间内所有历史 anchor。

## 6. 前端信息架构

管理页一级标签调整为：

- **已保存**：用户明确要求长期保留，可新建、编辑、置顶、删除。
- **来自聊天**：后台归纳的可变历史，可查看来源，编辑后转为已保存。
- **待确认**：需要人工确认的候选，确认后进入已保存。
- **图谱**：保留为高级探索视图，不再承担主要管理入口。

后续聊天界面需要补齐“已记住 / 撤销 / 编辑”和“本回答使用了 N 条记忆”的即时反馈；这是下一阶段最高优先级，而不是继续扩展图谱。

## 7. 调研取舍

- [ChatGPT Memory FAQ](https://help.openai.com/en/articles/11146739-how-does-reference-saved-memories-work)：采用 saved memory 与 chat history 两层产品模型。
- [LangMem](https://github.com/langchain-ai/langmem)：借鉴热路径工具与后台抽取/归并分离；不引入其 LangGraph 运行时。
- [Mem0](https://github.com/mem0ai/mem0)：借鉴抽取、更新、搜索的 memory layer 思路；当前不引入额外 embedding 与向量存储依赖。
- [Graphiti](https://github.com/getzep/graphiti)：借鉴事实来源和时间有效性；当前不引入图数据库。
- [Letta](https://github.com/letta-ai/letta) / [MemGPT](https://arxiv.org/abs/2310.08560)：适合有内存层级与自主工具调用的 stateful agent；WeKnora 普通 RAG 对话不需要完整 Agent OS。
- [LongMemEval](https://arxiv.org/abs/2410.10813)：把成功指标定义为信息抽取、跨会话推理、时间推理、知识更新和应当拒答时的克制。
- [LoCoMo](https://arxiv.org/abs/2402.17753)：用于长对话、跨 session、时间与因果问题；其逐 turn 证据标注支持本方案的 exact provenance 设计。

## 8. 是否真的能产生强大作用

可以，但作用集中在少数高价值场景：稳定回答偏好、身份与工作背景、持续项目状态、用户明确决策、跨会话未完成事项。它不会让模型“无限记忆”，也不能靠保存更多内容自动获得更强推理。

上线价值必须由评测证明，而不是由记忆条数或图谱节点数证明。最低评测集包含：

- 明确保存后跨会话命中；删除后不再命中。
- 不同属性并存；同一属性更新；旧事实不覆盖新事实。
- 时间问题、跨 session 组合问题、无答案时拒答。
- 错误召回率、有效召回率、最终答案提升率。
- P50/P95 召回延迟、每轮注入 token、后台抽取调用率与成本。
- 用户对“为什么记住、为什么使用、如何删除”的可理解度。

只有当最终答案提升率显著为正，且错误召回、延迟和成本在预算内，才应继续扩展自动记忆；否则默认保持“只记我要求的”是更诚实的产品选择。
